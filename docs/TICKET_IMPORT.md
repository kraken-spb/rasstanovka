# Импорт билетов на тестовом HR

В «Перевахте» кнопка с иконкой билета открывает загрузку PDF, JPEG/JFIF и PNG. Несколько файлов обрабатываются фоновым сервисом `ticket-worker`; веб-запрос не ждёт OCR. Исходники доступны только загрузившему их пользователю. Распознавание выполняется локально через Poppler и Tesseract (русский, английский, узбекский).

После обработки пользователь проверяет пассажира, сотрудника, направление, номер билета и каждый участок маршрута. Затем отмечает строки и подтверждает их. Сохранение выбранной партии атомарно; повторное подтверждение того же запроса не создаёт дубль. Сохраняются исходник, реквизиты, участки маршрута, плановая поездка и запись аудита. Фактическая явка и стадия сотрудника не меняются.

Доступ: администратор, супер-администратор, перевахта. Поиск и подтверждение учитывают текущую область СМУ пользователя. Сопоставление сравнивает ФИО, явные связи проекта с транспортными пунктами и ближайшие плановые даты. Равнозначные кандидаты не выбираются автоматически. Администратор задаёт связи и варианты названий/коды городов внутри панели; без них направление выбирают вручную.

Ограничения: 12 МБ и 12 страниц на файл, до шести ожидающих обработку файлов на пользователя, до 50 подтверждений за запрос. Год в неполной дате подставляется только из явно заполненного поля загрузки. Неизвестные формы билетов и незаполненные даты требуют ручного ввода. Один файл подтверждается как один билет одного пассажира; обнаруженные несколько пассажиров требуют разделения исходного файла или ручной проверки. Отдельные файлы авиа и ЖД не объединяются автоматически в одну поездку. Повтор номера сохранённого билета блокируется, включая случаи переоформления.

Схема PostgreSQL 29 добавляет `workforce_ticket_jobs`, `workforce_project_travelpoints`, `workforce_tickets`, `workforce_ticket_segments` и использует существующую `workforce_movements`. Миграцию нужно выполнять до совместного запуска `app`, `report-worker` и `ticket-worker` версии 29. Worker в `compose.staging.yaml` ограничен 2 CPU / 768 МБ; нужны общий том `/app/data` и временный каталог `/tmp`. Оригиналы сохраняются в приватном `ticket-import` внутри тома; автоматическое удаление исходников не предусмотрено.

При откате схема 29 остаётся: предыдущему образу требуется совместимый gate 29. Нельзя запускать неизменённый старый образ с gate 28 или автоматически восстанавливать старый дамп поверх новых пользовательских данных.
