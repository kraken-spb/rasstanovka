# Проверяемые выпуски

## Проверка исходников

Запустить из корня проекта `python tools/run_checks.py`. Нужны Python 3.12, зависимости из `requirements.txt` и Node.js. Команда выполняет полный набор Python-тестов, проверку UTF-8 и JavaScript-тесты. Если `seed.json` отсутствует, на время проверки используется синтетический `seed.example.json`; существующий файл не заменяется.

GitHub Actions выполняет те же проверки на Linux и Windows для push и pull request. После их успешного завершения собирается Docker-образ и проверяются запуск с пустой базой, защита API, вход, справочники и пустой отчёт. Workflow не получает производственных секретов и ничего не устанавливает на VPS. Actions закреплены на конкретных коммитах.

## Подготовка выпуска

1. Выпускать только проверенный коммит из чистой рабочей копии. Записать полный SHA коммита и идентификатор предыдущего образа.
2. Собрать образ с тегом, содержащим полный SHA, и меткой `org.opencontainers.image.revision`. Пример: `docker build --label org.opencontainers.image.revision=COMMIT_SHA -t crewplacement:COMMIT_SHA .` Подставить реальный SHA; не использовать `latest` как идентификатор выпуска.
3. Проверить именно этот образ: `python tools/smoke_image.py crewplacement:COMMIT_SHA`. Проверка запускает собственный временный контейнер без производственных томов и затем удаляет его.
4. Для переноса между машинами сохранить образ через `docker save` и загрузить через `docker load`, записав и сверив его идентификатор. Метка коммита не гарантирует побайтовую воспроизводимость повторной сборки: базовый Python-образ и транзитивные зависимости пока не закреплены полностью.
5. Перед установкой создать согласованную копию производственной SQLite через `sqlite3.Connection.backup`, проверить её и сохранить текущую конфигурацию запуска. На сервере совместить только согласованные изменения конфигурации; не заменять её локальной копией вслепую.
6. Запустить web и Telegram из одного проверенного образа. Для production Compose явно задать обоим сервисам этот тег через временный override, затем использовать `up -d --no-build`. Производственные `.env` и том данных сохраняются.
7. Проверить HTTPS, состояние контейнеров, вход, права, выбранную дату расстановки и согласованность отчёта. Записать результат вместе с SHA и временем установки.

## Откат

Сначала определить, совместима ли текущая схема базы с предыдущим приложением. При совместимой схеме переключить оба сервиса на сохранённый предыдущий образ с `--no-build`, не заменяя том данных. Если схема несовместима, остановить запись и подготовить отдельный план восстановления: замена базы старой копией удалит изменения, сделанные после копирования, поэтому автоматического восстановления поверх действующей базы нет.

Разделение запуска и миграций базы остаётся следующим этапом. До него запуск образа выполняет существующую инициализацию схемы; перед выпуском это нужно учитывать отдельно.
